# Decision Log

Record fixes, workarounds, and intentional trade-offs here. A pre-commit hook (`scripts/hooks/pre-commit`) scaffolds a placeholder entry on any code commit that lacks one, and blocks commits whose decisions.md still contains an unfilled placeholder. Bypass (sparingly): `git commit --no-verify`.

Each entry follows this shape:

- **Symptom:** what the user / future reader experienced or saw.
- **Fix:** what was done.
- **Surfaces:** greppable tokens (file paths, symbol names) so future debugging can find this entry via `grep -r <token> docs/decisions.md`.
- **Watch:** what could go wrong next, or a related edge case. Use "None" if nothing applies.
- **Commit:** the commit SHA the Fix landed in (filled at commit time, can be "(pending)").

**Never include secrets, tokens, connection strings, or PII in entries — this file is committed.**

## 2026-09-05 — Per-page projection: every page true to its own scale bar (Stage 9B)
- Symptom: `validate` failed `scale-consistency` on any wide atlas — worst footprint error 0.695% against a 0.5% tolerance for the ~100 km Lincoln→Omaha cover grid at 1:100,000. Reproduced on a plain `--bbox` of the same extent, so it predated the locations work.
- Root cause (measured, not assumed): NOT transverse-Mercator scale distortion, which is only ~0.002% at these distances. `buildPageGrid` projected the whole extent through ONE projector centred on the extent, and away from that central meridian **meridian convergence** (γ ≈ Δλ·sin φ) rotates each page rectangle relative to the lat/lng axes. `AtlasPage.bbox` is axis-aligned, so the box that contains the rotated rectangle inflates by roughly `(W·cos γ + H·sin γ)/W`. A diagnostic sweep at 1:100,000 on Letter measured the error growing linearly with distance from the central meridian: 0.173% at 0 km, 0.363% at 20 km, 0.723% at 40 km, 1.082% at 60 km. Location pages never showed it because `buildLocationPage` already built its own projector per page.
- Fix: new `pageBBoxAround(center, halfW, halfH)` in `projection.ts` — builds the projector **about that page's own centre** and returns the AABB. `buildPageGrid` still lays page centres out on one shared lattice (so spacing and `overlap` stay exact) but derives each page's bbox from its own centre; `buildRouteAtlas` does the same for `R#` corridor pages, which run furthest off any one meridian; `buildLocationPage` now shares the helper. Measured after: a flat 0.173%–0.175% wherever the page sits, independent of extent width. Also removed the duplicated `planeRectToBBox` from both `grid.ts` and `route.ts`.
- Trade-off (deliberate): adjacent pages no longer share exactly coincident bbox edges — they overlap/gap by that same fraction of a page (~0.17%, ~30 m at 1:100,000). Page-to-page continuity is carried by the `neighbors` ids, not by geometric coincidence, whereas the scale bar is a promise about ground truth on the printed sheet; per-page truth is the one worth keeping. The residual 0.173% is the unavoidable box-around-a-curved-quad term and would only go away by giving `AtlasPage` a rotated footprint instead of an AABB.
- Verified: new `scale-fidelity.test.ts` (4 tests) pins that a wide grid validates, that the worst error does not grow with extent width (a ~250 km grid is within 0.05% of a narrow one), that long-route corridor pages stay true, and that location pages hold at high latitude / far longitudes. atlas-core 59, map-sources 29, render-cli 40, worker 6; typecheck clean. ## 2026-09-09 — Tile fetches get a UA, a timeout, retries and a concurrency cap; a mostly-blank panel now fails the render

- Symptom: `apps/api/Program.cs` registered no exception handler at all. Endpoints caught their own validation exceptions — but only the ones whose authors thought of it, and only the type they thought of: `ProjectEndpoints` and `LocationEndpoints` catch theirs, while `GeneratedPdfEndpoints`, `LandmarkEndpoints`, `GeocodeEndpoints`, `RenderEndpoints` and `TileEndpoints` catch nothing. ## 2026-09-09 — SSRF in the tile-source registry: authorisation on the way in, egress restriction on the way out
- Symptom: `POST /api/tile-sources` was anonymous and stored any `SourceUrl`; `GET /api/tiles/{source}/{z}/{x}/{y}` then made the server fetch that URL and **returned the body to the caller**. A full SSRF with response reflection — point a source at `http://169.254.169.254/latest/meta-data/` and the API reads cloud instance credentials on your behalf; point it at an internal host and it is a port scanner that answers 200 or 502. Anyone who could reach the API could do this.
- Two controls, because either alone is insufficient. Authorisation stops strangers reaching the registry; egress restriction stops the fetch being dangerous even when the caller is authorised (a leaked admin key, or a source row already in the database, must not become a metadata read).
- **Egress, the load-bearing half.** Validating the URL string is not enough and cannot be: an attacker controls their own DNS, so a hostname that resolves to a public address at registration can resolve to `127.0.0.1` at fetch time (rebinding), and a public URL can 302 to a private one. So enforcement is at the socket — a `SocketsHttpHandler.ConnectCallback` on both tile HttpClients that runs `TileEgressPolicy.IsBlockedAddress` against the address actually being connected to, on every connection including every redirect hop; `AllowAutoRedirect = false` besides, since no tile endpoint needs redirects and following one is the other half of the same bypass. The callback vets **every** address a name resolves to and then connects to those vetted addresses rather than re-resolving the hostname, which would reopen the race it just closed. Blocked: loopback, 0/8, 10/8, 100.64/10, 169.254/16, 172.16/12, 192.168/16, 192.0.0/24, 198.18/15, multicast/reserved, IPv6 loopback/link-local/ULA, and IPv4-mapped IPv6 (`::ffff:127.0.0.1`) which is otherwise a one-line bypass.
- **Authorisation.** This API has no authentication of any kind — no `AddAuthentication`, no identity — and inventing one is a product decision, not an audit fix. `AdminApiKeyGate` is a shared key on the registry's POST/PUT/DELETE (reads stay anonymous; the web app lists sources and listing was never the hole). It **fails closed**: with no key configured the registry is read-only, so an operator who never read the setting gets something safe rather than something anyone can write to. Fixed-time comparison, because this key guards the thing that decides where the server makes outbound requests. When real auth arrives this is one call to delete.
- Registration-time validation is kept, but only to give a human a readable error instead of a silent 502 later — it is explicitly *not* the defence. It throws the new `TileSourceUrlPolicyException` → 400, distinct from `TileSourceValidationException` → 409 ("this key is taken"), so `ExceptionMapping` reads as documentation.
- **The trap that nearly broke a feature:** a `pmtiles` source may legitimately name a *local archive* (`fixture.pmtiles`, or `file:///…`), which `PmTilesFetcher` resolves inside `TileCache:PmTilesDir` under its own path-confinement guard. A naive "must be an absolute http(s) URL" rule rejects every local map package. Validation is therefore kind-aware: local paths and `file://` are allowed for `pmtiles` only, and a *remote* pmtiles archive is still subject to the address policy.
- **What this does NOT stop**, stated plainly: (1) a *public* host that is itself sensitive — the deny-ranges only cover private space, so a host allowlist (`Tiles:AllowedHosts`) is the real answer and a deployment should set one; (2) exfiltration *to* an attacker-controlled public host, since the fetchers may still reach the public internet by design; (3) anything at all when `Tiles:AllowPrivateNetworks=true`, the documented local-dev escape hatch; (4) an attacker who already has the admin key from registering a source on a public host that redirects... no — redirects are refused, but they can still register any public host; (5) SSRF through the *other* HTTP clients in this app (Overpass, Nominatim, the render worker), which take their base URLs from configuration rather than from user input and so are not the same class of hole, but are not covered by this policy either.
- Tests: `TileEgressPolicyTests` (address classification incl. the IPv4-mapped bypass and the just-outside-the-range boundaries, scheme rules, allowlist, and the pmtiles local-archive carve-out) and `AdminApiKeyGateTests` (fail-closed, no prefix match, case sensitivity) run without Docker. Substituting the pre-fix behaviour — a policy that blocks nothing and a gate that authorises everything — fails **30 of 79**. Three `Api` integration tests were added too (anonymous create refused and not stored, anonymous delete refused, authorised create still refuses a blocked URL); those need Testcontainers and **have not been run on this machine**.
- Surfaces: dotnet/JourneyBook.Infrastructure/Tiles/TileEgressPolicy.cs, IsBlockedAddress, TryValidateTemplate, dotnet/JourneyBook.Infrastructure/DependencyInjection.cs, CreateGuardedHandler, apps/api/AdminApiKeyGate.cs, apps/api/Endpoints/TileSourceEndpoints.cs, dotnet/JourneyBook.Application/TileSources/ITileSourceService.cs, TileSourceUrlPolicyException, dotnet/JourneyBook.Infrastructure/TileSources/TileSourceService.cs, EnsureUrlAllowed, apps/api/ExceptionMapping.cs, dotnet/JourneyBook.Tests/{TileEgressPolicyTests,AdminApiKeyGateTests}.cs, dotnet/JourneyBook.Tests/Api/{PostgisApiFactory,TileSourcesApiTests,PmTilesTilesApiTests}.cs, .env.example
- Watch: the gate is a **breaking change** for any client that registers tile sources — they must now send `X-Admin-Key`, and with no key configured they cannot register at all. `PostgisApiFactory.CreateAdminClient()` is how the integration suites keep working. The `ConnectCallback` bypasses `SocketsHttpHandler`'s pooled DNS behaviour and does its own `Dns.GetHostAddressesAsync` per connection; that is a small extra resolution cost on a cache miss, paid only by the tile fetchers.

## 2026-09-09 — The map panel was never actually cropped to the bbox
- Symptom: `renderMapPanel` builds a mosaic of tiles and then `.extract()`s the bbox window out of it. It does not. `sharp` applies operations in **pipeline order, not call order**, and an `extract` chained onto a `composite` is treated as a pre-extract on the *input* image: the blank canvas was cropped first, then the tiles were composited onto that crop at their original full-mosaic offsets. ## 2026-09-11 — `tileBaseUrl` was scheme-checked and nothing else, so the worker was an outbound fetch primitive for anything that could reach it
- Symptom: Audit F03, the half left open. `tileBaseUrl` is the one render input that makes a process issue an HTTP request to a destination the input chose, and it was guarded by `/^https?:\/\//i` in the engine and `{"pattern": "^https?://"}` in the worker's JSON schema. That refuses `file://` and `gopher://` and nothing else: `http://db:5432/`, `http://api:8080/api/admin/...` and `http://169.254.169.254/latest/meta-data/` all match it. The worker takes this field straight off an unauthenticated request body, so the only thing between a caller and an internal fetch was that the worker's port is `expose`d rather than published — which the audit calls, correctly, a deployment accident rather than a control.
- Fix: one shared `tileBaseUrlError` (`packages/render-cli/src/tile-url.ts`) in two layers, split by WHO is speaking.
  - **Structural, always on, engine included:** parse with `new URL` rather than pattern-match, require http(s), refuse embedded credentials, refuse a query string or fragment (the base is a path prefix — `renderMapPanel` appends `/{source}/{z}/{x}/{y}` to it, so a query cannot survive the concatenation and accepting one buys a 404 storm instead of one clear refusal).
  - **Destination, at the worker's HTTP boundary only:** refuse IP literals that are not globally routable — loopback, RFC1918, CGNAT 100.64/10, link-local including 169.254.169.254, multicast, reserved, and the IPv6 equivalents including v4-mapped forms — plus the `localhost` name. Parsing first is what makes this work: the WHATWG URL parser normalises `http://2130706433/`, `http://0177.0.0.1/`, `http://0x7f.1/` and `http://127.1/` all to `127.0.0.1` before the check sees them, and a regex or a `startsWith("http://127.")` would have missed every one.
  - **Operator allowlist:** `TILE_BASE_URL_ALLOWLIST` on the worker, set by compose to `http://api:8080/api/tiles` — the single destination the API ever sends. When set, nothing else is accepted; when unset it means "no allowlist configured", NOT "permit nothing", so a deployment that has not been told about the variable keeps working under the weaker rules.
- Why the destination rules are worker-only: `render-cli`'s caller is the operator typing the command, who can already curl anything the process can reach, and `--tile-base-url http://localhost:5180/api/tiles` is a documented local workflow — `render.test.ts` renders through `http://127.0.0.1:1/tiles` for exactly that reason. A guard that refused it would be refusing the person it is protecting.
- Why an allowlist entry OVERRIDES the non-routable check: an operator who writes `http://127.0.0.1:5180/api/tiles` into the allowlist has named that destination deliberately. Without that, the guard is a deny-all with extra words and the local-dev topology has no way back in. The refusal message names `TILE_BASE_URL_ALLOWLIST` so the remedy travels with the refusal.
- Shown red-then-green at the worker boundary: with `render-route.ts` reverted to HEAD, four probes failed — the cloud metadata address, loopback in four spellings, `http://10.0.0.7:5432/`, and a host the allowlist does not name. All four failed with **502, not 400**: the pre-fix worker had already left the process and tried the fetch, which is the finding stated as a test result. Two acceptance controls (`http://api:8080/api/tiles`, a public tile server) were green before and after, which is what they are for. One probe — embedded credentials — was green in that run too, because the engine half of the fix was already built into `render-cli/dist`; it is evidence for the structural layer, not the destination layer.
- A guard that fires is a guard that can break something, and this one did, immediately: the pre-existing `[CONTROL] writes tiles under the cache directory the operator configured` went red because its fixture used `http://127.0.0.1:9/tiles`, now refused before any tile is fetched. That control exists to notice exactly this and it did. The two cache tests now use a routable name; they are about where tiles are WRITTEN, and `fetch` is stubbed in both.
- Surfaces: packages/render-cli/src/tile-url.ts, tileBaseUrlError, parseTileBaseUrlAllowlist, packages/render-cli/src/render.ts, validateInput, services/render-worker/src/render-route.ts, services/render-worker/src/server.ts, TILE_BASE_URL_ALLOWLIST, infra/compose/docker-compose.yml
- Watch: hostnames other than `localhost` are NOT resolved and never will be here — the check is synchronous, and resolve-then-fetch is defeated by DNS rebinding anyway. The allowlist is the only control for names, which is also the only thing that can tell `http://api:8080/api/tiles` (intended, private) from `http://db:5432` (not). Second: the allowlist match is an origin+path-prefix match, so `http://api:8080/api/tilesX` is refused while `http://api:8080/api/tiles/usgs-topo` is permitted; a trailing-slash-only difference is normalised. Third: the C# tile proxy is unaffected — it never takes a base URL from a caller.

## 2026-09-11 — The worker was a stateless renderer, so nobody could know it was on page 12 of 60
- Symptom: `POST /render` held its connection open for the whole render. Only the worker knows how far a render has got, and it had nowhere to put that; only the worker can stop a render, and nothing could ask it to. ADR 0006 named the protocol this needs and deferred it. This is it — ADR 0007.
- Fix: `POST /render` answers **202** with `{ jobId, state, statusUrl }` and a `Location` header; `GET /jobs/{id}` returns the live record (`state`, `page`, `pageCount`, `phase`, and on completion `outputPath`/`attribution`); `DELETE /jobs/{id}` aborts the render. The registry (`jobs.ts`) is in memory, for the same reason ADR 0006 gave for the API's queue: a job is not restartable, so a persisted "rendering" row would only let a restarted worker report progress for a render that is definitely not happening. A job that dies with the process is reported by its absence — the poll gets 404 — which is true.
- What did NOT move, and this was the main design constraint: everything judgeable before a job exists still answers 400 on the POST. The schema, the tile-base-URL policy and `outputPath` confinement already did; `assembleContract` is now run synchronously too, so an unknown scale preset, a malformed bbox, margins that leave no map box and an extent over `MAX_ATLAS_PAGES` all stay 400s with the engine's own wording instead of becoming a 202 followed by a failed job someone has to go and read. It costs one repeat of pure geometry — milliseconds against minutes of tile fetching — and it is what stops the worker and the engine holding two definitions of a valid request.
- Failure kind is now a FIELD on the job, decided at the catch that saw the exception while its type was still available, not a substring match re-derived downstream. `cancelled` is a state, not a flavour of `failed`: a cancel left nothing on disk AND is what the user asked for, and reporting the second as the first is the failure this protocol exists to end.
- Concurrency: the HTTP connection used to be the back-pressure and the job protocol removes it, so `MAX_ACTIVE_JOBS` (default 4) refuses the 5th with 429. The API sends one at a time; this is a bound against anything else that can reach the port.
- Shutdown aborts every job in flight before closing the server. Without that, renders detached from their requests keep fetching tiles for an atlas nobody will be able to read.
- Probes, each proving it reached its subject (anchor unique, patched line echoed off disk, `services/render-worker/dist` md5 required to change): dropping `signal` from the `renderAtlas` call — RED; recording a cancel as `failed` — RED; wiring `onProgress` to a no-op — RED.
- Controls: the existing `[CONTROL] accepts the exact payload the C# API sends` still passes (now 202); a `DELETE` arriving after the render completed answers 200 with `completed` rather than claiming to have cancelled something.
- Two existing tile-cache tests were asserting on a render that had not started — `app.inject` now returns at acceptance. Both now wait for the job to settle. That is the first thing this protocol change broke, and it broke a `[CONTROL]`, which is what a control is for.
- Surfaces: services/render-worker/src/jobs.ts, JobStore, services/render-worker/src/render-route.ts, services/render-worker/src/server.ts, services/render-worker/src/render-route.test.ts, services/render-worker/src/render-input.test.ts
- Watch: a render is cancellable only between pages, so a `basemap: false` render passes its last checkpoint before the 202 is even written and is effectively uncancellable — honest, because such a render takes a second. Second: `JobStore` retention is 15 minutes and the cap is 500 records; a client that never polls leaves its outcome to be swept. Third: the API is the only client and there is no auth on the worker, so `MAX_ACTIVE_JOBS` is the only thing between the port and unbounded renders.

## 2026-09-11 — The API followed a render it could neither measure nor stop
- Symptom: `IRenderWorkerClient` was one blocking HTTP call. Progress could not be reported because the API had none to report (it knew only that a call was outstanding), and cancel could not be offered because aborting that call would have left the worker rendering.
